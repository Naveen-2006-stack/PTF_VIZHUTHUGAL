2. RESOLUTION OF REACT 19 SSR HYDRATION MISMATCH ERROR
--------------------------------------------------------------------------------
- Error Reported:
  Console Error: "A tree hydrated but some attributes of the server rendered HTML
  didn't match the client properties. This won't be patched up."
  Diff snippet:
    <body
      className="min-h-full flex flex-col font-sans bg-[#F8FAFC] text-[#1E293B]"
    - data-new-gr-c-s-check-loaded="14.1328.0"
    - data-gr-ext-installed=""
    >
  Source File: `src/app/layout.tsx` (Line 42)

- Root Cause Analysis:
  Browser extensions (specifically Grammarly) inject custom client-side attributes
  (`data-new-gr-c-s-check-loaded` and `data-gr-ext-installed`) onto the document
  `<body>` tag before React 19 client hydration completes. Because server-side
  rendering produces clean HTML without these extension attributes, React 19 flags
  a critical attribute hydration mismatch.

- Technical Fix Implemented:
  File Modified: `src/app/layout.tsx`
  Added `suppressHydrationWarning` to both `<html>` and `<body>` tags:
  ```tsx
  <html lang="en" className={`${plusJakartaSans.variable} ${inter.variable} h-full`} suppressHydrationWarning>
    <body suppressHydrationWarning className="min-h-full flex flex-col font-sans bg-[#F8FAFC] text-[#1E293B]">
      <AuthProvider>
        {children}
      </AuthProvider>
    </body>
  </html>
  ```
- Outcome: Completely eradicated hydration mismatch warnings while preserving React 19 fast refresh.

10. STAFF/MENTOR COMPLETE ISOLATION ARCHITECTURE
--------------------------------------------------------------------------------
Responsibility Definition:
`STAFF_MENTOR` portal access is strictly confined to Dr. APJ Abdul Kalam Special Class
daily attendance. Staff mentors have ZERO access to marks, personal profiles, leave,
scholarships, or administrative tools.

Enforced Across 3 Defense Layers:
1. Database Row Level Security (RLS):
   - `public.subject_marks`: Removed staff from SELECT/INSERT/UPDATE policies. Staff querying
     marks receives 0 rows. Attempted mutations fail immediately.
   - `public.leave_requests` & `public.permission_requests`: RLS grants access only to
     student owner or `is_admin()` / `is_ptf_secretary()`. Staff receives 0 rows.
   - `public.scholarship_applications`: Staff receives 0 rows.
   - `public.profiles`: Users can read only their own profile.

2. Backend API Gating:
   - `/api/attendance/abdul-kalam`: Validates caller is `STAFF_MENTOR`, `SUPER_ADMIN`, or `SEMI_ADMIN`.
   - All other management APIs (`/api/import/*`, `/api/staff/reassign`) reject `STAFF_MENTOR` with HTTP 403.

3. Frontend UI Navigation & Route Guards:
   - `src/components/navigation/Sidebar.tsx`: Renders only 3 navigation items for `STAFF_MENTOR`:
     1. Dashboard (`/dashboard`)
     2. Abdul Kalam Attendance (`/attendance/abdul-kalam`)
     3. Attendance History (`/attendance`)
   - `src/app/(portal)/layout.tsx`: Route guard automatically redirects `STAFF_MENTOR` away from any
     unauthorized URL directly to `/attendance/abdul-kalam`.
   - `src/app/(portal)/academics/ct-marks/page.tsx`: Explicit lockout card blocks staff view.

11. STUDENT ACADEMIC WORKFLOW & CYCLE TEST (CT) MARKS CORRECTION
--------------------------------------------------------------------------------
Location: `src/app/(portal)/academics/ct-marks/page.tsx`
Table: `public.subject_marks`

Workflow:
1. Student Self-Entry:
   - Students select Semester, Subject, Test (CT 1, CT 2, CT 3), Enter Marks, and Max Marks.
   - Proof Upload: Students upload marksheets directly to private bucket `academic-proofs`
     under path `${studentId}/${Date.now()}_CT${testNumber}.${ext}`.
   - Actions: "Save as Draft" (`DRAFT`) or "Submit for Verification" (`SUBMITTED`).

2. Status Lifecycle:
   `DRAFT` -> `SUBMITTED` -> `UNDER_REVIEW` -> `VERIFIED` / `CORRECTION_REQUIRED` / `REJECTED` -> `LOCKED`

3. Modification Rules:
   - While `DRAFT` or `CORRECTION_REQUIRED`: Student can modify marks, re-upload proof, and resubmit.
   - When `VERIFIED` or `LOCKED`: Student CANNOT edit marks. Read-only verified state displayed.

4. Administrator Verification:
   - Super Admin and Semi Admin review submissions in their review console.
   - Proof Viewing: Generates 120-second cryptographic signed URLs from private storage.
   - Decisions:
     * "Verify & Lock": Sets `status = 'VERIFIED'`, logs `verified_by` and `verified_at`.
     * "Request Correction": Sets `status = 'CORRECTION_REQUIRED'` with remarks.
     * "Reject": Sets `status = 'REJECTED'` with remarks.
   - All status transitions log an immutable event in `public.audit_logs`.

15. DAILY ATTENDANCE ENGINE & SINGLE-SESSION-PER-DAY UNIQUE CONSTRAINT
--------------------------------------------------------------------------------
Location: `src/app/(portal)/attendance/abdul-kalam/page.tsx` & `src/app/api/attendance/abdul-kalam/route.ts`
Table: `public.attendance`

Schedule:
- Morning Session: 5:30 AM - 7:00 AM
- Evening Session: 5:30 PM - 7:00 PM
- Allowed Statuses: `PRESENT`, `ABSENT`, `LATE`, `EXCUSED`

Critical Constraint Enforcement (Maximum 1 Session / Day):
1. Database Level:
   `CONSTRAINT uq_student_attendance_date UNIQUE (student_id, attendance_date)`
   PostgreSQL enforces that a student cannot have more than one attendance record per date,
   preventing duplicate morning + evening entries.
2. Business Logic & API Layer:
   - API queries for existing records on `attendance_date`.
   - If Morning was marked, attempting Evening returns HTTP 409 `DUPLICATE_DAILY_ATTENDANCE`.
   - If Evening was marked, attempting Morning returns HTTP 409 `DUPLICATE_DAILY_ATTENDANCE`.
   - Catches PostgreSQL error `23505` to prevent concurrent race condition duplicates.
3. Frontend UI Feedback:
   - Attendance roster checks today's records.
   - If student was already marked in another session, row is locked with badge:
     `🔒 Locked in [SESSION]` and controls are disabled.
4. Next-Day Attendance:
   - Next-day attendance (`attendance_date = date + 1`) operates cleanly.

16. DATABASE TRIGGERS & PRIVILEGE ESCALATION PREVENTION
--------------------------------------------------------------------------------
Function: `public.prevent_role_escalation()`
Trigger: `trg_prevent_role_escalation` on `public.profiles`

Vulnerability Addressed:
Standard RLS update policies on `public.profiles` permit users to update their own row (`id = auth.uid()`).
Without column-level controls, a user could manipulate the payload to include `role: 'SUPER_ADMIN'`.

Trigger Implementation:
```sql
CREATE OR REPLACE FUNCTION public.prevent_role_escalation()
RETURNS TRIGGER AS $$
BEGIN
    IF auth.uid() IS NULL OR (auth.jwt() ->> 'role') = 'service_role' THEN
        RETURN NEW;
    END IF;

    IF NEW.role IS DISTINCT FROM OLD.role AND NOT public.is_super_admin() THEN
        RAISE EXCEPTION 'Access Denied: You cannot modify your own role or permissions.';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER trg_prevent_role_escalation
BEFORE UPDATE ON public.profiles
FOR EACH ROW
EXECUTE FUNCTION public.prevent_role_escalation();
```
Verification:
Tested via `scripts/test-comprehensive-rules.mjs` (Test 9). Direct role escalation attempts
are aborted by the database trigger and role remains unchanged.
