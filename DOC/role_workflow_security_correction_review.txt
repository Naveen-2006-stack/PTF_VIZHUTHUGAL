4. STAFF_MENTOR COMPLETE ISOLATION ARCHITECTURE
================================================================================
Isolation has been implemented at three independent defense layers:

1. Database Row Level Security (RLS):
   - Table `public.subject_marks`:
     Policy: `is_staff_mentor()` completely removed from SELECT, INSERT, UPDATE.
     Querying `subject_marks` as STAFF_MENTOR returns 0 rows.
   - Table `public.leave_requests` & `public.permission_requests`:
     Policy: Access granted only to student owner or `is_admin()` / `is_ptf_secretary()`.
     STAFF_MENTOR receives 0 rows.
   - Table `public.scholarship_applications`:
     Policy: Access granted only to student owner or Admin. STAFF_MENTOR receives 0 rows.
   - Table `public.profiles`:
     Policy: Users can read only their own profile.

2. API Authorization Layer:
   - Route `/api/attendance/abdul-kalam`:
     Validates caller role is `STAFF_MENTOR`, `SUPER_ADMIN`, or `SEMI_ADMIN`.
     Students and PTF_SECRETARY receive HTTP 403 Forbidden.
   - Route `/api/import/*` & `/api/staff/reassign`:
     Validates caller role is `SUPER_ADMIN`.
     STAFF_MENTOR receives HTTP 403 Forbidden.

3. Frontend Navigation & Route Guards:
   - File `src/components/navigation/Sidebar.tsx`:
     Renders ONLY 3 navigation items for `STAFF_MENTOR`:
     1. Dashboard (`/dashboard`)
     2. Abdul Kalam Attendance (`/attendance/abdul-kalam`)
     3. Attendance History (`/attendance`)
   - File `src/app/(portal)/layout.tsx`:

     route outside attendance directly to `/attendance/abdul-kalam`.
   - File `src/app/(portal)/academics/ct-marks/page.tsx`:

5. STUDENT ACADEMIC WORKFLOW & CYCLE TEST (CT) MARKS CORRECTION
================================================================================
Code Location: `src/app/(portal)/academics/ct-marks/page.tsx`
Table: `public.subject_marks`

Workflow Steps:
1. Student Self-Entry:
   - Students click "Enter CT Mark" on their mark portal.
   - Inputs: Semester, Subject, Test Number (CT 1, CT 2, CT 3), Mark Obtained,
     Maximum Mark (e.g. 50), Remarks.
   - Proof Document Upload: Student uploads an image or PDF of their college marksheet.
     The file is uploaded directly to the private Supabase Storage bucket `academic-proofs`
     under path `${studentId}/${timestamp}_CT${testNumber}.${ext}`.
   - Actions: Student can "Save as Draft" (`status = 'DRAFT'`) or "Submit for Verification"
     (`status = 'SUBMITTED'`).

2. Status Progression Lifecycle:
   `DRAFT` -> `SUBMITTED` -> `UNDER_REVIEW` -> `VERIFIED` / `CORRECTION_REQUIRED` / `REJECTED` -> `LOCKED`

3. Modification Rules:
   - While `DRAFT` or `CORRECTION_REQUIRED`: Student can edit scores, re-upload proof,
     and resubmit.
   - When `VERIFIED` or `LOCKED`: Student CANNOT edit the record. The UI displays a
     locked green badge with verified timestamp.

4. Administrator Verification:
   - Super Admin and Semi Admin review submissions in their marks console.
   - Private Proof Inspection: Admin clicks "View Proof", which generates a 120-second
     server-signed URL via `supabase.storage.from('academic-proofs').createSignedUrl()`.
   - Actions:
     * "Verify & Lock": Sets `status = 'VERIFIED'`, records `verified_by` and `verified_at`.
     * "Request Correction": Sets `status = 'CORRECTION_REQUIRED'` with administrative remarks.
     * "Reject": Sets `status = 'REJECTED'` with remarks.
   - All status transitions log an immutable event in `public.audit_logs`.

6. STUDENT ACCOUNT PROVISIONING & ONE-TIME PROTECTED CREDENTIAL EXPORT
================================================================================
API Route: `src/app/api/import/students/route.ts`
Database Function: `public.create_student_account` (PL/pgSQL SECURITY DEFINER)
UI Console: `src/app/(portal)/admin/students/page.tsx`

Import Workflow:
1. Authorization Check:
   Endpoint verifies that `auth.uid()` belongs to a user with role `SUPER_ADMIN`.
   All non-super-admins receive HTTP 403 Forbidden.

2. File Validation:
   - Supports CSV and XLSX parsing via PapaParse and SheetJS.
   - Validates required fields: Student Name, University Register Number, Campus Code,
     Department Code, Course Code, Year, Academic Year.
   - Validates that Campus exists in `public.campuses`.
   - Validates that Department belongs to the specified Campus.
   - Validates that Course belongs to the specified Department.
   - Validates that Register Number does not already exist in `public.students`.

3. Staff Mapping Validation:
   - If a `staff_code` or `staff_id` is supplied in the import row, verifies that the
     staff account exists in `public.staff_profiles` and is active.
   - Verifies that the staff member belongs to the same campus as the student.

4. Automatic PTF ID Generation:
   - Inspects existing students to find the highest sequence number.
   - Automatically generates sequential institutional IDs: `PTF001`, `PTF002`, `PTF003`...

5. Crypto-Secure Temporary Password Generation:
   - Generates random temporary passwords using Node.js `crypto.randomBytes()`.
   - Ensures complexity: uppercase, lowercase, numbers, and symbols (e.g. `Ptf@8k#M2x9a`).

6. Atomic Database Provisioning (`public.create_student_account`):
   - Creates row in `auth.users` with encrypted bcrypt password (`extensions.crypt()`).
   - Creates row in `auth.identities` with email provider data.
   - Creates row in `public.profiles` with role `'STUDENT'` and `must_change_password = TRUE`.
   - Creates row in `public.students` with academic details and status `'ACTIVE'`.
   - Creates initial row in `public.staff_student_assignments` if staff mapping was provided.

7. One-Time Protected Credential Export:
   - The API response payload returns:
     `{ success: true, importedCount: N, credentials: [...], errors: [...] }`
   - Super Admin can immediately click "Download Credentials CSV".
   - Export Columns: `PTF ID, Student Name, Register Number, Campus, Department, Staff Code, Staff Name, Temporary Password, Email`.
   - Temporary passwords are NEVER stored in plaintext and cannot be retrieved from the
     database after modal closure.
   - Student is forced to change password upon first login (`/change-password`).

9. DAILY ATTENDANCE ENGINE & SINGLE-SESSION-PER-DAY CONSTRAINT
================================================================================
Code Location: `src/app/(portal)/attendance/abdul-kalam/page.tsx`
API Route: `src/app/api/attendance/abdul-kalam/route.ts`
Table: `public.attendance`

Class Schedule:
- Morning Session: 5:30 AM – 7:00 AM
- Evening Session: 5:30 PM – 7:00 PM
- Allowed Statuses: `PRESENT`, `ABSENT`, `LATE`, `EXCUSED`

Critical Constraint Implementation:
Rule: A student may attend ONLY ONE Abdul Kalam session per day.

Enforcement Mechanism:
1. Database Level:
   `CONSTRAINT uq_student_attendance_date UNIQUE (student_id, attendance_date)`
   PostgreSQL enforces uniqueness across the composite key `(student_id, attendance_date)`
   regardless of session type.

2. Business Logic & API Layer:
   - When marking attendance, the API checks for any existing record on `attendance_date`.
   - If Morning was already marked, attempting Evening fails with error code
     `DUPLICATE_DAILY_ATTENDANCE` and HTTP 409.
   - If Evening was already marked, attempting Morning fails with HTTP 409.
   - Catches PostgreSQL error code `23505` to prevent concurrent race conditions.

3. Frontend UI Feedback:
   - The attendance roster checks today's records for all sessions.
   - If a student was marked in the other session, the row is locked with a badge:
     `🔒 Locked in [SESSION]` and action buttons are disabled.

4. Next-Day Attendance:
   - Next-day attendance (`attendance_date = date + 1`) is allowed and operates normally.

10. DATABASE TRIGGERS & PRIVILEGE ESCALATION PREVENTION
================================================================================
Database Function: `public.prevent_role_escalation()`
Database Trigger: `trg_prevent_role_escalation` on `public.profiles`

Vulnerability Addressed:
Standard RLS update policies on `public.profiles` allow users to update their own profile
row (`id = auth.uid()`). Without strict column-level controls, a malicious student could
execute `supabase.from('profiles').update({ role: 'SUPER_ADMIN' })` and gain full admin access.

Trigger Implementation:
```sql
CREATE OR REPLACE FUNCTION public.prevent_role_escalation()
RETURNS TRIGGER AS $$
BEGIN
    -- Allow service_role or administrative migrations when auth.uid() is null
    IF auth.uid() IS NULL OR (auth.jwt() ->> 'role') = 'service_role' THEN
        RETURN NEW;
    END IF;

    -- If role is changed and actor is not super admin, abort!
    IF NEW.role IS DISTINCT FROM OLD.role AND NOT public.is_super_admin() THEN
        RAISE EXCEPTION 'Access Denied: You cannot modify your own role or permissions.';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER trg_prevent_role_escalation
BEFORE UPDATE ON public.profiles
FOR EACH ROW
EXECUTE FUNCTION public.prevent_role_escalation();
```

Verification:
Tested directly via `scripts/test-comprehensive-rules.mjs` (Test 9). A student attempting
to update their own role receives an exception, and the role remains `STUDENT`.

12. LEAVE & PERMISSION APPROVAL WORKFLOW & PDF SLIP GENERATION
================================================================================
Code Location: `src/app/(portal)/leave-permission/page.tsx`
Tables: `public.leave_requests`, `public.permission_requests`, `public.approval_documents`

Workflow Rules:
1. Application Submission:
   Students submit Leave (Medical/Personal) or Permission (On-Duty/Events).
   Status is initialized as `SUBMITTED`.

2. Administrative Decision:
   - Super Admin or Semi Admin reviews request in review modal.
   - If Approved:
     * Request status updated to `APPROVED`.
     * Generates a unique slip number (e.g. `PTF-LV-2026-849201`).
     * Inserts record into `public.approval_documents` with student ID, approver details,
       and timestamp.
     * Dispatches an in-portal notification to the student.
     * Enables official PDF slip download via `generateApprovalSlipPDF()`.
   - If Rejected:
     * Request status updated to `REJECTED` with admin remarks.
     * NO approval slip record is generated.
     * UI displays "No PDF Issued". Student cannot download approval document.
   - If Correction Requested:
     * Status updated to `CORRECTION_REQUIRED`. Student can edit dates/reason and resubmit.

3. Staff Mentor Lockout:
   Staff/Mentor role is completely locked out of the leave and permission module.
